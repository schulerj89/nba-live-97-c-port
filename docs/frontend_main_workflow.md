# Frontend main recovery

`nba97_frontend_main` recovers FEONLY `0x80028800..0x80028B8B` from the 908-byte source range whose SHA-256 is `a9325ac1de6cf8da7bd5a43d95da2f2e61bfc586cd3f265824d3e519cb42b208`. It executes all 227 source instructions with MIPS delay-slot order, byte-granular knownness, retained guest memory, operation/access/instruction journals, and a full 32-GPR/HI/LO machine. The result distinguishes a returning GAMELOAD callback from a terminal GAMELOAD transfer; a transferred run stops after the dynamic JALR callback and does not execute the source epilogue.

The owner exposes every original child call as one of 50 typed source-site contracts. Each event records the call PC, delay PC, live target, argument count, per-site invocation, and target program. The 49 fixed calls remain FEONLY. The dynamic `0x80028B68` JALR uses the word copied to guest `0x801E0000` and is explicitly GAMELOAD. Unknown or unaligned dynamic targets fail only after the JALR and NOP have entered the instruction trace. Callback refusal and malformed callback state retain the callback's mutations and the exact executed prefix.

`nba97_frontend_main_with_recovered_dispatch_entry` composes site `0x80028AA0` through the committed frontend-dispatch-entry adapter. That adapter in turn invokes the committed frontend dispatcher. The other 49 services stay in the caller's typed callback. `Nba97FrontendMainAdapterProgress` records the exact wrapper event and full machine observed at the main adapter boundary, plus fresh wrapper and dispatcher diagnostics. A rejected nested binding cannot expose diagnostics from an earlier successful invocation.

`nba97_frontend_main_from_overlay_entry` is the explicit synthetic parent boundary. It accepts only FEONLY JAL `0x8007B838`, delay `0x8007B83C`, entry `0x80028800`, invocation one, zero arguments, and known aligned RA `0x8007B840`. The production parent and production service bindings remain outside this recovery.

`nba97::captureFrontendMain()` returns a JSON receipt. Its stable top-level fields are `program`, `address`, `inclusive_end`, `bytes`, `instructions`, `source_sha256`, `completed`, `accepted`, `result`, `contract_failure`, `classification`, `gameplay_shown`, `fixture_contract`, `parent_call`, `branch_state`, `loader_state`, `memory`, `main`, `wrapper`, `dispatcher`, `user_setup`, `final_machine`, and `next_unbound_boundary`. `main` contains exact counts, the complete instruction and access journals, and a 65-entry call sequence; the wrapper entry is the event and machine captured at the actual adapter boundary. `dispatcher.call_sequence` is checked against its exact 42-call whitelist. Word values serialize as `{word, known_mask}` and bytes/results serialize numerically.

The capture uses generated RAM and typed synthetic services. The startup fixture publishes dispatcher launch flag 1 at guest `0x80015098`, the allocation calls return a generated address, the loader returns a generated 4096-byte buffer and size, the main copy callback copies the complete buffer with knownness, and the copied first word supplies the GAMELOAD entry. Source and destination checksums and the observed copy count appear in `loader_state`. The GAMELOAD callback returns without showing gameplay. `UserSetupSession` supplies native input acceptance inside the recovered dispatcher path.
